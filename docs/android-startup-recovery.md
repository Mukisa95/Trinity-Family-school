# Returning to Trinity

Ordinary Home/Recents returns keep the live activity, WebView, page and query cache. An ordinary full restart opens the dashboard (`/parent` for parents). Explicit notification, widget and launcher shortcut destinations take precedence once and are consumed before recreation. Existing privacy locking still applies.

All explicit native launches use `AppEntry.intent`. Warm destinations use `trinity-android-navigate` with a UUID `requestId` and internal `url`. The existing web shortcut navigator announces `navigationReady`, handles the request with Next's router and sends `navigationHandled`. Duplicates are acknowledged without repeating navigation. Older web bundles retain the shortcut protocol and a single full-navigation fallback after document completion and a two-second readiness grace. Visibility changes never trigger that fallback.

Prepared public interface shells open directly from the service-worker cache for Android, installed web apps and ordinary browsers. Authenticated ordinary browser sessions prepare their dashboard/login shell after initial painting; installed/native preparation stays with its existing owner. Each deployment's worker prepares current HTML, immutable assets and matching build-keyed route records before publishing replacement HTML. Repeated launches reuse already prepared content for that worker version. Failed preparation keeps the previous complete shell. No private school records, credentials or application-user profile enter these HTML caches. Existing clients are never automatically navigated on a worker update.

Startup distinguishes restored Firebase identity, saved viewing and verified live access. A matching non-anonymous identity and an unexpired scoped viewing receipt can open saved data after three seconds of delayed verification. A transient verification failure can open that same eligible saved view sooner. The existing seven-day receipt limit, school/account/role/family/permissions/class scope and privacy lock remain in force. Reading the receipt never renews it. Saved-only viewing expires even while the page remains open and cannot enable editing, queued Firestore writes or query mutations.

Token and staff profile verification each have an eight-second deadline. Unknown service failures remain retryable; authoritative credential/access failures still clear the session. The session API distinguishes unavailable verification (503) from confirmed invalid access (401), and never caches either response. Pending verification retries after 5, 15 and 60 seconds, then once per minute while visible and connected, and on reconnect. Generation checks reject late responses after a retry, account change or unmount. A manual retry retires the previous attempt.

When restoration cannot establish a usable saved workspace, the existing branded startup surface offers Retry after eight seconds rather than signing out or spinning indefinitely. Normal startup appearance and fade are unchanged. Welcome/personalisation completion is independent and unchanged.

Device-local problem reports now include random process/activity/document identifiers, creation and entry categories, bounded resume/startup-to-interactive durations and a broad historical Android process-exit category where supported. They never contain raw account keys, arbitrary URLs, token contents or private records. Browser visibility and document lifecycle timings remain separate from Android process lifecycle evidence.

Run `npm run test:startup-resume` for the executable shell, deadline, endpoint, auth and entry-router checks. Run the existing workspace welcome/recovery, Android offline-navigation, push-click, PDF bridge and release build checks before publishing. Browser fixtures simulate service boundaries; a successful browser run is not proof of real Android lifecycle or performance. Physical acceptance still requires Home/Recents, screen lock, process recreation, all explicit entry points, slow-online/offline networking, PDF work and camera return testing.

Deployment is separate: prepare both signed school APKs locally and wait for an explicit push/deployment request.
